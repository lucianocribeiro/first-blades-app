# FB-F3-14 — Migración: tabla de solicitudes de ausencia (patrón purgatorio)

> **Tipo:** build de migración (solo esquema). **NO** incluye feature ni UI.
> **NO** aplicar a producción en esta tarea. CI valida; el `db push` es un paso aparte con runbook, después del merge y de la auditoría de esquema **FB-F3-AUD-14**.

## Objetivo

Crear la tabla que habilita el flujo **solicitud → aprobación → efecto** (patrón purgatorio) para solicitudes de ausencia. Es la base de **Días de Trámite** (primer tipo que la usa) y queda preparada para el resto de los motivos de ausencia de Fase 4.

Esta tarea entrega **solo** la migración: tabla + enum de estado + RLS + constraints + tests. Sin formulario, sin cola de aprobación, sin escritura al calendario (eso es FB-F3-15/16).

2. **Enum de estado de purgatorio**: ¿ya hay un enum reutilizable de un purgatorio previo (documentos / pasajes) con `pendiente / aprobado / rechazado` o similar? Si existe, **reusarlo**, no duplicar. Reportar el nombre y los valores exactos.
3. **Tabla de solicitudes previa**: ¿existe alguna tabla de solicitudes (pasajes/documentos) cuyo patrón de nombres y columnas convenga seguir por consistencia? Alinear a esa convención.
4. **Identificador de empleado**: confirmar qué columna usa `rotation_assignments` para el empleado (`user_id`) y cuál es la PK de `profiles` (`id`). 5. **Inventario de enums/tablas** para actualizar el drift detector (`migration.test.ts`) con `toEqual` exacto.

Reportar el resultado de la inspección **antes** de proponer el DDL final.

## Alcance de la migración

Tabla nueva **`solicitudes_ausencia`** (ajustar nombre a la convención real del repo si hay una tabla de solicitudes previa). Forma **propuesta** (ajustar tipos/nombres a la convención verificada en la inspección):

- `id uuid PRIMARY KEY DEFAULT gen_random_uuid()`
- `user_id` (mismo identificador que `rotation_assignments`) **NOT NULL**, FK al empleado solicitante
- `motivo motivo_ausencia NOT NULL` — discriminador; **reusa el enum existente `motivo_ausencia`**. En esta fase la feature solo usará `dia_tramite`; la tabla acepta el resto para Fase 4.
- `fecha_solicitada date NOT NULL` — la fecha puntual pedida (una por solicitud, sin rango)
- `estado <enum de estado> NOT NULL DEFAULT 'pendiente'` — reusar el enum de purgatorio existente; si no existe, crear `estado_solicitud` con `{pendiente, aprobada, rechazada}` (usar la misma nomenclatura del purgatorio previo si lo hay)
- `nota text` — nota opcional del solicitante
- `motivo_rechazo text` — se completa solo al rechazar
- `resuelto_por` uuid FK a `profiles(id)` — admin que resolvió (nullable hasta resolver)
- `resuelto_at timestamptz` — nullable hasta resolver
- `created_at timestamptz NOT NULL DEFAULT now()`

**Constraints (validar por catálogo con `pg_get_constraintdef`, no "existe alguna"):**

- CHECK: `estado = 'rechazada'` ⇒ `motivo_rechazo IS NOT NULL`
- CHECK: `estado IN ('aprobada','rechazada')` ⇒ `resuelto_por IS NOT NULL AND resuelto_at IS NOT NULL`
- **Índice único parcial** para evitar solicitudes pendientes duplicadas de la misma fecha/motivo:
  `UNIQUE (user_id, fecha_solicitada, motivo) WHERE estado = 'pendiente'`
  (permite volver a solicitar la misma fecha si la anterior quedó `rechazada`; no bloquea distintos motivos).

> No hay FK ni columna que apunte a la fila del calendario: al aprobar se hace un upsert sobre `rotation_assignments (user_id, fecha)`; el saldo se **deriva** del calendario, la tabla de solicitudes es la capa de flujo, no la de conteo.

## Datos / RLS / seguridad (invariantes purgatorio)

RLS habilitada. Invariante central: **nada llega a `aprobada` sin acción explícita de un admin**; ningún no-admin puede setear ni modificar `estado`.

- **Empleado**
  - INSERT: solo filas propias (`user_id = auth.uid()`) y forzadas a `estado = 'pendiente'`. No puede insertar por otro ni con otro estado.
  - SELECT: solo sus propias solicitudes.
  - UPDATE de `estado`: **denegado**.
- **Supervisor**
  - SELECT: su equipo (`user_id` de sus subordinados vía `supervisor_id`) + sí mismo. Solo lectura sobre solicitudes; no aprueba.
- **Administrador**
  - SELECT: todas.
  - UPDATE: puede pasar a `aprobada` / `rechazada` y setear `resuelto_por` / `resuelto_at` / `motivo_rechazo`.

Notas de implementación:
- **Filtro de app superpuesto a la RLS** en la query del supervisor (`.eq` explícito por equipo + su fila), no confiar solo en la RLS como scope.
- Lecturas/escrituras de feature con `createServerClient()` (RLS aplicada). No usar `createAdminClient()` acá.
- Errores visibles, nunca degradados a `[]`.

## Tests (verificación por CI, no local)

- La migración corre limpia contra Postgres fresco en CI. Integración **hard-fail** si no puede correr (nunca skip silencioso).
- **Drift detector** (`migration.test.ts`): enum(s), tabla y columnas nuevas reflejadas con `toEqual` exacto (actualización intencional del inventario).
- **Constraints por catálogo** (`pg_get_constraintdef`): CHECK de `motivo_rechazo`, CHECK de `resuelto_*`, e índice único parcial de pendientes (rechaza duplicado pendiente; permite re-solicitar tras `rechazada`; permite distinto motivo).
- **RLS bajo el JWT de cada rol** (`asUser`, leyendo por id directo sin filtro de app):
  - Empleado inserta pendiente propia → OK.
  - Empleado intenta insertar por otro `user_id` → rechazado.
  - Empleado intenta UPDATE de `estado` → rechazado.
  - Empleado no ve solicitudes ajenas → 0 filas.
  - Supervisor ve su equipo + propio; no ve fuera de equipo → 0 filas.
  - Admin ve todo y puede aprobar/rechazar.
- **No** aplicar la migración. CI valida, no pushea.
