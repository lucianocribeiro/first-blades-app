## 7. Inspección de alineación (resultado verbatim, vía MCP Supabase read-only, proyecto `simfemdkrkdbumefcxei`)

Se leyó `resolver_ausencia_request` verbatim en prod (`pg_get_functiondef`) para el patrón de auditoría del molde. Fragmento relevante (rama `aprobar`):

```sql
SELECT COALESCE(jsonb_agg(jsonb_build_object(
         'fecha', fecha,
         'estado_dia_previo', estado_dia,
         'motivo_ausencia_previo', motivo_ausencia
       ) ORDER BY fecha), '[]'::jsonb)
INTO v_calendario_previo
FROM public.rotation_assignments
WHERE user_id = v_request.user_id
  AND fecha BETWEEN v_request.fecha_inicio AND v_request.fecha_fin;

v_new_data := jsonb_build_object(
  'estado', 'aprobado',
  'calendario_pisado', v_calendario_previo
);

INSERT INTO public.audit_log (actor_id, action, table_name, record_id, old_data, new_data)
VALUES (auth.uid(), 'ausencia_approved', 'ausencia_requests', p_request_id, v_old_data, v_new_data);
```

**Veredicto: `resolver_ausencia_request` agrupa.** Una sola fila de `audit_log` por resolución, con `table_name='ausencia_requests'`, `record_id=p_request_id`, y todos los días pisados embutidos como un array jsonb (`new_data.calendario_pisado`) — **no** genera filas con `table_name='rotation_assignments'` ni una fila por día. Diverge del patrón por-día que este fix le da a `resolver_pasaje_request`.

**Consecuencia:** `resolver_ausencia_request` **no se tocó** en este fix — sigue en prod, agrupada, sin cambios. La divergencia entre ambas funciones (ausencia agrupa, pasaje audita por-día) queda documentada acá para que la decisión de alinearlas (si corresponde) sea una pieza aparte y gateada por Luciano — alinear la de ausencia tocaría una función ya en producción, fuera del alcance "no aplica a producción" de este ciclo.

## 8. Resultado (implementación)

**Fix 1 — `audit_log` por día**, en `supabase/migrations/0016_resolver_pasaje.sql` (editado in-place — la migración aún no está en prod, así que el fix se aplica sobre el mismo 0016 en vez de sumar un 0017 para un cambio no pusheado):

- La fila de transición de la request (`action='pasaje_approved'`, `table_name='pasaje_requests'`, `record_id=p_request_id`) se mantiene, ahora sin `calendario_pisado` embutido — sólo `{estado: 'aprobado'}`.
- Dentro del `FOREACH v_dia IN ARRAY v_request.dias_viaje`, antes del upsert se captura el estado previo de ESE día puntual (`SELECT ... INTO v_cal_old_data ... WHERE user_id = empleado_id AND fecha = v_dia` — `NULL` si no había fila). El `INSERT ... ON CONFLICT ... DO UPDATE` ahora termina en `RETURNING id INTO v_cal_id`, capturando el id real de la fila de `rotation_assignments` (insertada o actualizada). Inmediatamente después, un `INSERT INTO audit_log` con `action='pasaje_calendario_sobrescrito'`, `table_name='rotation_assignments'`, `record_id=v_cal_id`, `old_data=v_cal_old_data`, `new_data={fecha, estado_dia:'en_viaje', motivo_ausencia:null, motivo_otros_texto:null, es_estimado:false}`.
- Conteo resultante de `audit_log` por aprobación: **1 (transición) + N (una por cada día de `dias_viaje`)**. Rechazar sigue generando sólo 1 fila (transición), sin tocar el calendario ni el audit por-día.
- Todo sigue dentro del cuerpo único de la función — ningún `BEGIN`/`COMMIT`/`SAVEPOINT` explícito nuevo; un solo `RAISE` en cualquier punto (incluido cualquier INSERT/UPDATE del loop) revierte todo el bloque, transición incluida.

**Fix 2 — atomicidad bajo `asUser`**, en `tests/integration/resolver-pasaje-request.test.ts`:

- Se eliminó el helper `asAdminSuperuser` (quedó sin uso).
- Los dos casos "falla el upsert de `rotation_assignments`" y "falla el INSERT a `audit_log`" ahora siguen el mismo patrón que el tercer caso (fallo a mitad de array): el `ALTER TABLE ... ADD CONSTRAINT` de fixture corre en una conexión `setupClient` aparte (rol propietario de la tabla, no `authenticated`), committeada y limpiada explícitamente en un `finally` (`DROP CONSTRAINT IF EXISTS`); la invocación afirmada de `resolver_pasaje_request` corre dentro de `asUser(IDS.admin)` — rol `authenticated` + claims de admin, el camino de ejecución real del RPC.
- Los tres casos siguen afirmando rollback total: `estado` de la request sin cambios, `audit_log` sin filas nuevas, `rotation_assignments` sin filas nuevas.

**Tests actualizados/nuevos en el mismo archivo:**
- Happy path (`REQ_DIAS_SUELTOS`, sin sobrescritura real): se agregó la aserción de las 3 filas de audit por-día, todas con `old_data=NULL` (días libres) — cubre "aprobar sin sobrescritura" del DoD.
- Rechazar: se agregó la aserción de que no se genera ninguna fila `action='pasaje_calendario_sobrescrito'`.
- Sobrescritura (`REQ_SOBRESCRITURA`): reescrita para verificar la fila de transición (única, sin `calendario_pisado`) por separado de las 3 filas de audit por-día (correlacionadas por `record_id IN (SELECT id FROM rotation_assignments WHERE ...)`, ya que el `record_id` de estas filas ya no es el id de la request) — `old_data` exacto para 04-20 (`trabajando`) y 04-21 (`periodo_fuera_trabajo`+`vacaciones`), `NULL` para 04-22 (día libre).
