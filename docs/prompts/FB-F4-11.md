## 2. Alcance implementado

### 2.1 Config Playwright (`playwright.config.ts`)
- Chromium-only (ya lo era). Retries: 1 en CI (no 2 — determinismo, no enmascarar flakes), 0 en local.
- `webServer.command`: `npm run build && npm run start` en CI, `npm run dev` en local.
- Timeouts más generosos en CI (test 60s, expect 10s, action 15s, navigation 30s) — el runner corre Postgres + 7 servicios de Supabase + Next + Chromium en 2 vCPUs compartidas, más lento que un dev local.
- `trace: 'retain-on-failure'`, `screenshot: 'only-on-failure'`.

### 2.2 Seed determinístico (`supabase/seed-e2e.ts`, script `npm run seed:e2e`)
- Admin, supervisor y empleado a cargo (`supervisor_id`), credenciales por env (`E2E_ADMIN_EMAIL/PASSWORD`, etc.) — **nunca hardcodeadas**: en CI se generan al vuelo con `openssl rand -base64 24` dentro del job efímero (nunca persisten en el repo); en local, el desarrollador las setea en su shell antes de correr `npm run test:e2e` (documentado en `.env.example`).

### 2.3 Workflow de CI (`.github/workflows/ci.yml`, job `e2e`)
Pasos: checkout → setup Node → setup Supabase CLI → `npm ci` → instalar Chromium (`playwright install --with-deps chromium`) → `supabase start` → exportar credenciales del Supabase local + generar credenciales e2e → **esperar a que `/auth/v1/health` responda de verdad** (paso agregado tras una corrida real que colgó por contención de CPU — `supabase start` puede reportar éxito con GoTrue/PostgREST todavía terminando de levantar) → `npm run seed:e2e` → `npm run test:e2e` (build+start+Playwright) → subir `playwright-report/` como artefacto (siempre, `if: always()`).

**Regla dura de seguridad:** el job sólo usa `NEXT_PUBLIC_SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` del Supabase **local** (`http://127.0.0.1:54321`, tomado de `supabase status`), nunca las de `.env.local`/prod. Sin `SUPABASE_DB_PASSWORD` de prod en ningún paso.

### 2.4 Cobertura e2e (`tests/e2e/`)
- `helpers.ts`: `login(page, role)` vía el form real; `exactLabel(text)` (ver §3); `resolveUserId`/`seedRotationAssignment`/`seedPendingAusencia`/`seedPendingPasaje` (seed vía `createAdminClient()`, retry-safe — ver §4).
- `auth.spec.ts`: login de los 3 roles + credenciales inválidas.
- `solicitudes.spec.ts`: empleado crea Solicitud de Ausencia (rango) y Solicitud de Pasaje (días discretos, botón "Agregar día").
- `aprobaciones.spec.ts`: admin ve la previsualización de sobrescritura, aprueba una ausencia y rechaza un pasaje (motivo requerido). Los pendientes se siembran directo por DB (no por UI) para quedar determinísticos e independientes del orden de specs.
- `modal-inert.spec.ts`: test dirigido a `<dialog>.showModal()` — ver §3 para el detalle de cómo quedó finalmente diseñado tras varias corridas reales.

### 2.5 `data-testid` / accesibilidad
- **No se agregó ningún `data-testid`.** Un único cambio no conductual: `aria-label="Días de viaje N"` en cada input de fecha dinámico de `SolicitudPasajeForm.tsx` (antes sin nombre accesible individual — mejora de a11y real, y de paso selector estable para e2e). No toca comportamiento ni JSX condicional.

## 3. El test dirigido a `<dialog>.showModal()` — por qué terminó así

El objetivo (§3.4 del prompt): probar la inertización del fondo y el foco atrapado — la clase de bug que jsdom (unit/RTL) no puede detectar porque no implementa el modal top-layer real del navegador. Ocho corridas reales en CI (todo el resto de la suite estable desde la corrida 4) fueron necesarias para depurar el test en sí, no la app:

1. **Fondo inertizado (click):** confirmado con `click({trial:true})` sobre un link del sidebar mientras el modal está abierto — nunca se vuelve "actionable" (el `::backdrop` nativo intercepta el hit-test). Estable desde la primera corrida en que se probó de forma aislada.
2. **Foco atrapado:** el enfoque inicial (`page.keyboard.press('Tab')` repetido, verificando `document.activeElement`) resultó **no confiable bajo CDP**: el primer Tab sintético sacaba el foco a `document.body` de forma reproducible, aun con el fondo ya confirmado inerte para click — un artefacto de cómo Chromium headless procesa un keydown de Tab sintetizado, no un bug de la app. Se reemplazó por una aserción más directa de la MISMA garantía: foco **programático** (`elemento.focus()` vía `page.evaluate`) sobre un elemento del fondo es un no-op mientras el modal está abierto (un elemento inerte rechaza foco por script, por spec) — estable en las corridas siguientes.
3. **Efecto colateral no relacionado:** el link del sidebar usado para las aserciones de fondo (`Sidebar.tsx`) dispara `onClick={onClose}` en **cualquier** click (pensado para cerrar el drawer mobile tras navegar, pero también colapsa el sidebar desktop a `w-0`). Navegar a `/aprobaciones` clickeando ese mismo link colapsaba el sidebar como efecto de ESE click, no del modal, confundiendo la aserción final ("vuelve a ser clickeable tras cerrar"). Se resolvió navegando con `page.goto()` en vez de clickear el link, y usando `trial:true` en ambos chequeos de actionability (nunca dispara el click real ni su efecto colateral).

Ninguno de estos tres hallazgos tocó código de la app — los tres eran del lado del test. El resultado final prueba la garantía real (inertización de click + inertización de foco programático) sin depender de la simulación de teclado.

## 4. Idempotencia de los seeds (retry-safe)

`test.beforeAll` puede re-ejecutarse si el único test de un `describe` falla y Playwright reintenta (retries:1 en CI) — un seed no-idempotente duplica filas o choca con constraints. Se ajustaron:
- `seedPendingAusencia`: si el INSERT choca con la exclusion constraint `ausencia_requests_no_solapamiento_pendiente` (23P01), busca y reusa la fila ya sembrada por el intento anterior en vez de tirar.
- `seedPendingPasaje`: sin exclusion constraint en `pasaje_requests` (por diseño, ver 0016) — buscaría duplicar en silencio; ahora busca primero por el marcador único (`destino`) y reusa si ya existe.
