## Alcance — decisiones de modelo tomadas (aplicar tal cual)

### 1. Modelo PER-DÍA de `rotation_assignments`
`rotation_assignments` se modela **por día**: una fila por `(profile_id, fecha)` con un único `estado_dia`.

- Si hoy existe con `fecha_inicio`/`fecha_fin` (rango), **adaptalo al modelo per-día de la forma menos destructiva posible** y documentá el approach en el PR (p. ej. una única columna `fecha`, o `fecha_inicio = lo garantice).
- Si la tabla está **vacía en prod**, migrá el esquema directo.
- **Antes de cualquier cambio destructivo (drop de columna con datos, borrado de filas), FRENÁ y reportá el estado real para decisión.** No borres datos por tu cuenta.

### 2. Columna `es_estimado`
Agregá a `rotation_assignments`:
```
es_estimado boolean NOT NULL DEFAULT false
```
Semántica: `true` = día futuro planificado (estimado); `false` = real. Un cron posterior (otra tarea) lo pasará a `false` cuando `fecha <= hoy + 7 días`. En esta tarea **solo se crea la columna**, no el cron.

### 3. Motivo obligatorio en `periodo_fuera_trabajo`
`motivo_ausencia` (nullable) es **REQUERIDO** cuando `estado_dia = 'periodo_fuera_trabajo'`. Aplicá esa regla con un **CHECK constraint a nivel de base** (no solo en la app):
- `estado_dia = 'periodo_fuera_trabajo'` ⇒ `motivo_ausencia IS NOT NULL`.
- `motivo_otros_texto` (nullable) aplica cuando `motivo_ausencia = 'otros'`.

### 4. `group_id` nullable, sin gestión de grupos
`group_id` queda **NULLABLE**. **No se construye gestión de grupos en Fase 3**; solo se preserva la columna/FK a `rotation_groups`.

### 5. Columna `dni` en `profiles`
Agregá a `profiles`:
```
dni text UNIQUE   -- NULLABLE
```
Es la clave de identificación para el import de historial (tarea posterior). **Nullable** para no romper filas existentes (Postgres permite múltiples NULL bajo UNIQUE); el admin poblará el DNI de los empleados actuales. **No agregar NOT NULL.**

### 6. Unicidad del roster
Aplicá `UNIQUE (profile_id, fecha)` en `rotation_assignments`: una sola fila de estado por empleado y día.

## Datos / RLS / Seguridad

### RLS (Constitución §6) — verificar y completar
Sobre `rotation_groups` y `rotation_assignments`, garantizar:

| Rol | Permiso |
|---|---|
| **Admin** | Acceso completo (SELECT/INSERT/UPDATE/DELETE) |
| **Supervisor** | `SELECT` de su propio calendario **+ el de su equipo** (`profiles.supervisor_id = auth.uid()`). **SIN escritura.** |
| **Empleado** | `SELECT` **solo** de su propio calendario. **SIN escritura.** |

- Si la RLS ya existe pero no cubre exactamente esto, **ajustala en la migración**.
- La RLS es el **backstop**; el scope semántico de cada vista se superpondrá con filtro de app en la fase de UI (no en esta tarea).

### Seguridad

- Errores visibles, nunca tragados; nada de degradar a `[]` que oculte fallas de RLS/query.

## Tests

Actualizá `migration.test.ts` (inventario exacto de enums/tablas/columnas) para reflejar el nuevo estado esperado: columna `es_estimado`, columna `profiles.dni`, CHECK de motivo, UNIQUE `(profile_id, fecha)`. Mantené el detector **ESTRICTO** (que falle si el remoto diverge de lo esperado).

### Tests de RLS (integración, patrón Fase 2)
Usando `asUser` y clientes por rol:
- **Admin** escribe y lee cualquier fila de `rotation_assignments`.
- **Supervisor** lee su fila y las de su equipo; **NO** lee las de fuera de su equipo; **NO** escribe.
- **Empleado** lee solo su fila; **NO** lee la de otro; **NO** escribe.
- Para probar el bloqueo de lectura cruzada, leé **directo por id sin filtro de app**, de modo que el "0 filas" pruebe la RLS y no el filtro de aplicación.
- **CHECK constraint:** un `INSERT` de `periodo_fuera_trabajo` sin `motivo_ausencia` debe **fallar**.
