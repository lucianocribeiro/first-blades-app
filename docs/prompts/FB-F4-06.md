## 2. Alcance

### Fix 1 — previsualización de sobrescritura (Alto)
- **Ubicación:** `app/(app)/aprobaciones/page.tsx:109` (cálculo server-side) y `app/(app)/aprobaciones/AprobacionesTable.tsx:147` (render).
- Hoy: si la query a `rotation_assignments` falla, hace `console.error(...)` + `return`; la UI sólo muestra `SobrescrituraAviso` cuando hay días → "no se pudo calcular" es indistinguible de "no hay días a sobrescribir".
- **Fix:** propagar un **estado por request**, ej. `{ status: 'ok', days: DiaSobrescrito[] } | { status: 'error' }`. En la UI:
  - `status: 'ok'` con `days.length > 0` → `SobrescrituraAviso` con los días (como hoy).
  - `status: 'ok'` con `days` vacío → sin aviso (no hay nada que sobrescribir).
  - `status: 'error'` → copy visible **no bloqueante**: "No se pudo calcular la previsualización de sobrescritura." (es-AR, en `/lib/copy`).
- **No bloqueante en todos los casos:** aprobar/rechazar sigue disponible sea cual sea el estado de la previsualización. Sin locks, sin confirmación dura (se mantiene la decisión de `FB-F4-05`).

### Fix 2 — mail de resolución generalizado (Medio)
- **Ubicación:** `app/(app)/aprobaciones/ausencia-actions.ts:56`, `lib/email/ausencia-resolution-email.ts:27`, `lib/copy/index.ts:405`.
- **Fix:**
  - La action **re-lee** los campos necesarios para el mail: `motivo`, `fecha_inicio`, `fecha_fin`, `motivo_otros_texto` (si `otros`), además del destinatario. (Puede leerse la fila post-RPC, ya resuelta.)
  - Generalizar template + copy: subject e intro de **"solicitud de ausencia"** (no "día de trámite"); incluir **motivo amigable** (reusar el mapeo de `motivo-options.ts` / copy es-AR) y el **rango** `fecha_inicio`–`fecha_fin` (si `inicio = fin`, mostrar un solo día); incluir `motivo_otros_texto` cuando el motivo es `otros`.
  - Mantener el envío **best-effort post-commit**: un fallo de envío no revierte la RPC ni rompe consistencia; la app sigue siendo la fuente.
  - Día de trámite debe seguir leyéndose bien dentro del template generalizado (es un motivo más; rango de un día).

**No** tocar la RPC, el esquema, ni la lógica de scope de resolución (ya correcta). No convertir el mail en bloqueante.

## 6. Resultado (implementación)

**Fix 1 — contrato de estado:**
- `app/(app)/aprobaciones/page.tsx`: nuevo tipo `OverwriteStatus = { status: 'ok'; days: OverwriteDay[] } | { status: 'error' }`. El loop de previsualización por request setea `overwriteStatusByRequest` con `'error'` en fallo de query (antes: `console.error` + `return`, sin registrar nada) o `'ok'` con `days` (incluso `[]`) en éxito. Se propaga como prop `overwriteStatusByRequest` (antes `overwritesByRequest: Record<string, OverwriteDay[]>`).
- `app/(app)/aprobaciones/AprobacionesTable.tsx`: `DetalleCell` distingue los tres casos — `status:'error'` muestra `copy.aprobaciones.sobrescritura.error` (nuevo, es-AR); `status:'ok'` con `days.length > 0` muestra `SobrescrituraAviso` (igual que antes); `status:'ok'` con `days` vacío no muestra nada. Aprobar/Rechazar no dependen de este estado en ningún caso.

**Fix 2 — mail generalizado:**
- `lib/email/ausencia-resolution-email.ts`: `AusenciaApprovalEmailInput`/`AusenciaRejectionEmailInput` ahora llevan `fechaFin`, `motivoAusencia`, `motivoOtrosTexto?`. Reutiliza `formatRangoAusencia` y `motivoAusenciaLabel` de `lib/rotation/ausencia-display.ts` (mismos helpers que ya usa `MisSolicitudesTable`/`AprobacionesTable` — un solo mapeo motivo→copy amigable). El campo de motivo de rechazo (texto libre del admin) se renombró de `motivo` a `motivoRechazo` para no colisionar con el nuevo `motivoAusencia`.
- `lib/copy/index.ts`: `emails.ausenciaAprobada`/`ausenciaRechazada` generalizados — subject/intro pasan de "tu día de trámite" a "tu solicitud de ausencia"; `fechaLabel` reemplazado por `motivoLabel` + `periodoLabel`; en rechazo, el label del motivo del rechazo se renombró a `motivoRechazoLabel` para no chocar con el nuevo `motivoLabel` (motivo de la ausencia).
- `app/(app)/aprobaciones/ausencia-actions.ts`: `fetchRequestForNotification` ahora selecciona `fecha_fin, motivo_ausencia, motivo_otros_texto` además de `fecha_inicio` (post-RPC, misma fila ya resuelta — no se re-valida nada, solo se re-lee para el mail). `approveAusencia`/`rejectAusencia` pasan esos campos a los builders. El envío sigue siendo best-effort post-commit: la RPC ya commiteó antes de que este bloque corra.
