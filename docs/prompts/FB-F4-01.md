## 1. Objetivo

Reemplazar el bloqueo de duplicados exactos de `ausencia_requests` por un bloqueo de **solapamiento de rangos** entre solicitudes **pendientes** del mismo empleado, sin importar el motivo.

**Regla de negocio (cerrada con Luciano):**
- Un empleado **no puede tener dos solicitudes de ausencia `pendiente` cuyos rangos de fechas se solapen**, cualquiera sea el `motivo_ausencia`. Para pedir otra que se solape, primero hay que resolver (aprobar o rechazar) la pendiente.
- El no-solapamiento aplica **sólo entre `pendiente`**. Contra ausencias `aprobado` NO se bloquea: una ausencia aprobada puede sobrescribir días ya escritos (eso se maneja en la pieza de feature con una alerta de sobrescritura, fuera de esta migración).

## 4. Contenido de la migración (referencia — ajustar al esquema verificado)

```sql
-- 0014_ausencia_no_solapamiento.sql
-- No-solapamiento de rangos entre ausencias PENDIENTES del mismo empleado (cualquier motivo).
-- Reemplaza el índice de duplicados exactos por una exclusion constraint de rangos.

-- 1) btree_gist habilita el operador de igualdad (=) dentro de un índice GIST,
--    necesario para combinar user_id (=) con el solapamiento de rangos (&&).
CREATE EXTENSION IF NOT EXISTS btree_gist WITH SCHEMA extensions;

-- 2) Drop del índice viejo (sólo bloqueaba duplicados exactos por motivo).
DROP INDEX IF EXISTS ausencia_requests_pendiente_unica;

-- 3) Exclusion constraint: dos filas pendientes del mismo user_id no pueden
--    tener rangos [fecha_inicio, fecha_fin] que se solapen. Rango inclusivo en
--    ambos extremos: compartir un solo día ya es solapamiento.
ALTER TABLE ausencia_requests
  ADD CONSTRAINT ausencia_requests_no_solapamiento_pendiente
  EXCLUDE USING gist (
    user_id WITH =,
    daterange(fecha_inicio, fecha_fin, '[]') WITH &&
  )
  WHERE (estado = 'pendiente');
```

**Notas de implementación:**
- **Inclusividad del rango:** usar `daterange(..., '[]')` (ambos extremos inclusive). Dos ausencias que comparten un único día (una termina el 5, otra empieza el 5) **sí** se consideran solapadas — correcto.
- **Resolución de operadores:** si en la inspección las extensiones no viven en `extensions` o el operador `&&`/`=` no resuelve por search_path, ajustar el schema del `CREATE EXTENSION` a la realidad verificada. No hardcodear `extensions` si el repo usa otro schema.
- Si el `DROP INDEX` real requiere `IF EXISTS` con schema calificado, ajustarlo al nombre verbatim de la inspección.
- La migración debe ser **idempotente-segura para CI** (Postgres fresco): la extensión con `IF NOT EXISTS`, el índice con `IF EXISTS`.
