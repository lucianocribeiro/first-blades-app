## 2. Alcance implementado

### 2.1 Helpers convertidos (`lib/storage.ts`)

- **`validateDocumentFile`**: de `void` + `throw` a `ValidateDocumentFileResult = { ok: true } | { ok: false; error: string }`.
- **`createSignedUrl`**: de `Promise<string>` + `throw` a `CreateSignedUrlResult = { ok: true; url: string } | { ok: false; error: string }`.
- **`uploadDocument`**: de `Promise<{storagePath, signedUrl}>` + `throw` a `UploadDocumentResult = { ok: true; storagePath: string; signedUrl: string } | { ok: false; error: string }`. Internamente encadena `validateDocumentFile` y `createSignedUrl` — si cualquiera de los dos falla, propaga su `{ok:false, error}` tal cual (mismo shape, sin re-envolver el mensaje).

Ningún otro export de `lib/storage.ts` tira (`DOCUMENTS_BUCKET` es una constante). Sin cambios en la lógica de validación/subida en sí (mismos límites: 10 MB, mismos MIME permitidos) — solo cómo se comunica el resultado.

### 2.2 Llamadores adaptados (grep exhaustivo de `from '@/lib/storage'`)

```
app/(app)/mi-perfil/actions.ts:7   import { uploadDocument as storageUpload, createSignedUrl, validateDocumentFile } from '@/lib/storage';
tests/unit/storage.test.ts:2       import { validateDocumentFile, DOCUMENTS_BUCKET } from '@/lib/storage';
tests/unit/mi-perfil.test.ts:9     import { validateDocumentFile } from '@/lib/storage';
lib/purge.ts:2                     import { DOCUMENTS_BUCKET } from '@/lib/storage';
```

- **`app/(app)/mi-perfil/actions.ts`** — único caller productivo, 3 sitios:
  - `handleDocumentUpload`: el `try/catch` que envolvía `validateDocumentFile`/`storageUpload` (agregado en FB-F4-18 porque el helper tiraba) se reemplaza por `const validation = validateDocumentFile(...); if (!validation.ok) return { ok: false, error: validation.error };` y el mismo patrón para `storageUpload`. Comportamiento observable idéntico — el mensaje que llega al usuario es el mismo, solo que ahora viaja como valor de retorno desde el origen, no como excepción atrapada en el borde.
  - `uploadDocumentForEmployee`: mismo patrón.
  - `getSignedUrls`: el `try { ... } catch { result[path] = ''; }` alrededor de `createSignedUrl` pasa a `const r = await createSignedUrl(path); result[path] = r.ok ? r.url : '';` — mismo fallback a `''` en caso de fallo, sin cambiar el contrato externo de `getSignedUrls` (sigue devolviendo `Record<string,string>`, decisión de FB-F4-18 de no tocarlo se mantiene).
- **`lib/purge.ts`** — solo importa la constante `DOCUMENTS_BUCKET`, no una función que tire. Sin cambios.
- **`tests/unit/storage.test.ts`** / **`tests/unit/mi-perfil.test.ts`** — actualizados (ver §3).

**Ningún caller quedó sin adaptar.**

## 4. Decisión: `getSignedUrls` sigue devolviendo `Record<string,string>` con fallback `''`

No se convirtió `getSignedUrls` a `{ok,error}` — sigue siendo, por diseño de FB-F4-18, un caso donde el fallo no tiene un mensaje de usuario que mostrar (se omite la preview del documento, no se bloquea nada). Lo único que cambió es cómo consume el resultado ahora-no-throwing de `createSignedUrl` internamente; su propio contrato hacia `searchEmployees`/la UI no cambió.
