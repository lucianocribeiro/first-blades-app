## Hallazgo 1 (Medio, bloqueante) — El CHECK deja pasar whitespace no visible

**Qué pasa:** `btrim(x)` sin segundo argumento recorta espacios comunes, pero no tabulaciones ni saltos de línea. Un `contenido_texto` con un solo tab, o un `file_path` con un salto de línea, satisface el constraint. La regla de negocio "un procedimiento tiene que tener contenido real" no se cumple.

El criterio equivocado viene del prompt `FB-F5-02`, no de tu implementación.

**Qué hacer** (`supabase/migrations/0020_fase5_procedimientos.sql:76`):

Reescribí el CHECK usando un criterio que rechace **cualquier** string compuesto solo de whitespace. Usá la clase POSIX:

```sql
ADD CONSTRAINT procedures_contenido_presente
CHECK (
  (contenido_texto IS NOT NULL AND contenido_texto !~ '^[[:space:]]*$')
  OR (file_path IS NOT NULL AND file_path !~ '^[[:space:]]*$')
);
```

Requisitos:

- **Simétrico** en las dos ramas, mismo criterio exacto.
- Verificá que el operador de regex con patrón constante sea **inmutable** y por lo tanto válido dentro de un CHECK. Si por cualquier motivo Postgres lo rechaza, **frená y reportá** con el error textual; no lo sustituyas por una variante más débil.
- Un solo constraint. Sin duplicados ni `DROP` colgados.

**Tests a agregar**, además de los seis que ya existen. Casos negativos, el INSERT tiene que fallar:

- `contenido_texto = E'\t'` con `file_path` NULL
- `contenido_texto = E'\n'` con `file_path` NULL
- `file_path = E'\t'` con `contenido_texto` NULL
- `file_path = E'\n'` con `contenido_texto` NULL
- Un caso mixto: `E' \t\n '` (espacios, tab y salto combinados) en cada columna

Y **confirmá que los positivos siguen pasando**, en particular uno con contenido real que **contenga** tabs o saltos de línea en el medio (un procedimiento escrito con párrafos es exactamente eso). Este caso importa: si el fix rompe el contenido multilínea legítimo, es peor que el problema original.
