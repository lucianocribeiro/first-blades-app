# FB-F1-11 — Serializar la suite de integración + tripwire de seed

- **ID:** FB-F1-11
- **Fecha:** 20 de junio de 2026
- **Destino:** Claude Code
- **Propósito:** Que `mi-perfil.test.ts` deje de fallar contra Supabase real, eliminando la verdadera causa: los archivos de integración no corren realmente en serie y se pisan el seed vía `TRUNCATE`. Solo se toca infraestructura de test. No se modifica app, migraciones, policies ni aserciones de los tests.

## Contexto

La suite corre contra Supabase local (FB-F1-07 a FB-F1-09). `rls.test.ts`, `purge.test.ts` y `migration.test.ts` pasan; las 10 fallas restantes están todas en `mi-perfil.test.ts`:

- `INSERT INTO documents` → viola `documents_user_id_fkey` ("Key is not present in table profiles").
- `SELECT` de perfil/documento propio → 0 filas.
- `UPDATE` de admin → 0 filas afectadas.

FB-F1-10 reescribió el método de seed (UPDATE-from-VALUES → `INSERT ... ON CONFLICT`) y no cambió nada: dio idéntico en dos corridas.

## Causa raíz

El problema no es **cómo** se siembran los profiles, es que la suite **no corre en serie**.

`vitest.integration.config.ts` confía en `poolOptions.forks.singleFork: true` para serializar. Pero `singleFork` solo fuerza un único proceso worker; **no** garantiza ejecución secuencial de archivos. El switch canónico de Vitest para eso es `fileParallelism: false`, que no está seteado, así que queda en `true` por default. Los archivos pueden solaparse contra la misma base.

Cada archivo, en su `beforeAll`, llama a `setupTestDb()`, que arranca con:

```sql
TRUNCATE TABLE ... documents, profiles RESTART IDENTITY CASCADE
```

Cuando el `TRUNCATE` de otro archivo (`rls`/`purge`) se dispara mientras las filas recién sembradas de `mi-perfil` están vivas, las borra. De ahí la mezcla de síntomas: lecturas de filas propias de `mi-perfil` (`nombre='Juan'`, `DOC_CERT/OTROS/ESTUDIO`) que vuelven 0, y una ventana de carrera donde ni los profiles base están y caen los `INSERT documents` con FK.

`mi-perfil` es la víctima que más depende de filas que solo él crea y el que tiene el `beforeAll` más largo (está a mitad de seed cuando otro trunca). Por eso FB-F1-10 no podía arreglarlo: un `TRUNCATE` concurrente borra los profiles los siembres como los siembres.

## Cambios implementados

### (1) Serializar de verdad — `vitest.integration.config.ts`

Agregado `fileParallelism: false` dentro de `test`. Se conserva `singleFork`. Ahora el bloque `test` queda:

```ts
  test: {
    globalSetup: ['./tests/integration/global-setup.ts'],
    include: ['tests/integration/**/*.test.ts'],
    environment: 'node',
    globals: true,
    testTimeout: 30_000,
    hookTimeout: 60_000,
    // Integración: un único proceso (singleFork) Y archivos en serie
    // (fileParallelism:false). Ambos son necesarios: singleFork solo
    // garantiza un worker; fileParallelism:false garantiza que cada
    // archivo termine entero antes de que arranque el siguiente, para
    // que el TRUNCATE de un setupTestDb() no pise el seed de otro archivo.
    fileParallelism: false,
    pool: 'forks',
    poolOptions: {
      forks: { singleFork: true },
    },
  },
```

### (2) Tripwire de seed — `tests/integration/helpers.ts`

En `setupTestDb()`, después del paso 7 (los `GRANT ...`) y antes de `return client;`, se agregó:

```ts
  // 8. Tripwire: el seed base debe haber dejado exactamente 6 profiles.
  //    Corre como postgres (superusuario), así que ve todas las filas sin RLS.
  //    Si falla, el problema está en el seed o en un TRUNCATE concurrente
  //    de otro archivo — no lo escondemos en violaciones de FK posteriores.
  const { rows: tripwire } = await client.query(
    'SELECT count(*)::int AS n FROM public.profiles'
  );
  if (tripwire[0].n !== 6) {
    throw new Error(
      `setupTestDb: se esperaban 6 profiles tras el seed, hay ${tripwire[0].n}. ` +
      `Indica seed incompleto o TRUNCATE concurrente de otro archivo de test.`
    );
  }
```

## Verificación esperada

1. `npm run test:integration` localmente (con `supabase start` corriendo): los 4 archivos verdes, incluido `mi-perfil.test.ts`.
2. En CI (job `integration`): suite completa verde contra Supabase real.
3. El tripwire no debe dispararse. Si se dispara, su mensaje aparece en el log y nos dice exactamente que el seed quedó en N≠6.
4. No cambian resultados de los tests unitarios, typecheck, lint ni build.
