## 1. Objetivo

En `tests/integration/ausencia-no-solapamiento.test.ts`, los casos **"dos empleados distintos pueden tener pendientes solapadas"** (~línea 87) y **"una ausencia aprobada no bloquea una nueva pendiente"** (~línea 95) afirman la **inserción esperada** dentro de `asServiceRole(...)`. `service_role` bypassa la RLS, así que esos dos caminos permitidos no quedan probados por el mismo rol acotado que usa la app.

Corregir: la **inserción que se está afirmando** debe ocurrir bajo `asUser` (JWT del rol acotado). El cliente privilegiado sólo puede usarse para el **setup indispensable** que un no-admin no puede montar (ej. sembrar una fila `estado='aprobado'`, que la policy `ausencias_insert_non_admin` no permite a un no-admin).

## Nota de ejecución (Claude Code, delta contra §2)

`asUser`/`asServiceRole` (helpers.ts) siempre hacen `ROLLBACK` al cerrar cada llamada, así que dos llamadas separadas (ej. `asUser(A)` para sembrar, `asUser(B)` para afirmar) nunca ven las filas de la otra — la fila de A no sobreviviría para que B intente solaparla. Por eso, para los dos casos de este fix, la inserción de setup y la inserción que se afirma corren en la **misma transacción/conexión**, cambiando `request.jwt.claims` (vía un helper local `actAs`, mismo mecanismo que usa `asUser` internamente) y el `ROLE` de Postgres cuando hace falta el bypass de setup, dentro de un nuevo helper local `withSameTxClient` — sin tocar `helpers.ts` (fuera de alcance de esta pieza), y sin cambiar el resultado observable: sigue siendo RLS real vía `auth.uid()` para cada inserción que el test afirma, `service_role` solo para el setup indispensable de la fila `aprobado`.

- **"Empleados distintos":** ambas inserciones (empleado1 y empleado2) corren bajo `ROLE authenticated` + `actAs` con el JWT real de cada uno — ninguna usa privilegio.
- **"Aprobada no bloquea":** la fila `aprobado` se siembra con `ROLE service_role` (setup indispensable, comentado); la inserción que se afirma corre después, en la misma transacción, con `ROLE authenticated` + `actAs(employee3)`.

Casos preexistentes (4 variantes de bloqueo + no-solapada permitida) intactos, sin cambios — ya corrían bajo `asUser`.
