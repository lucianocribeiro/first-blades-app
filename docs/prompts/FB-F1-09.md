# FB-F1-09 — Fix: la migración 0004 no debe re-habilitar RLS en storage.objects

- **ID:** FB-F1-09
- **Fecha:** 19 de junio de 2026
- **Destino:** Claude Code
- **Propósito:** Que la migración `0004_rls_fixes.sql` aplique limpio contra el Supabase real. Quitar el `ALTER TABLE storage.objects ENABLE ROW LEVEL SECURITY`, que falla por ownership.

## Contexto

Con la integración corriendo contra Supabase real (FB-F1-07/08), `supabase start` aplica todas las migraciones. La 0004 fallaba en su primera sentencia:

```
ERROR: must be owner of table objects (SQLSTATE 42501)
ALTER TABLE storage.objects ENABLE ROW LEVEL SECURITY
```

En Supabase real, `storage.objects` pertenece al rol interno `supabase_storage_admin`. El rol de migración (`postgres` superusuario) puede CREATE/DROP POLICY sobre esa tabla, pero no puede ALTER TABLE sobre ella en lo que respecta al ownership. Supabase ya trae RLS habilitado en `storage.objects` por defecto, así que la sentencia era redundante e inofensiva en Supabase real — pero en la práctica aborta la migración.

La línea fue agregada en FB-F1-05 (hallazgo 03-01) para alinear la migración con el mock `setup.sql`, que ya fue retirado en FB-F1-07. El mock ocultaba el bug; el entorno real lo destapó.

## Cambio implementado

**`supabase/migrations/0004_rls_fixes.sql`:** eliminada la sentencia:
```sql
ALTER TABLE storage.objects ENABLE ROW LEVEL SECURITY;
```
y su bloque de comentario asociado.

Las `DROP POLICY IF EXISTS` + `CREATE POLICY` sobre `storage.objects` se conservan: son las que imponen el control de acceso real (supervisor solo propio, admin sube a cualquier carpeta) y aplican correctamente bajo el rol superusuario.

## Resultado esperado

`supabase start` aplica las 4 migraciones sin errores. La suite de integración llega a correr. Si persisten fallas de assertion, son hallazgos de lógica a reportar por separado.
