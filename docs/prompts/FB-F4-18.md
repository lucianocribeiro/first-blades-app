# FB-F4-18 — Fix: contrato return-based en las actions del flujo de documentos

> **Fase 4 · Cierre · Fix.** Para Claude Code, vía Luciano.
> Cierra el pendiente confirmado por `FB-F4-18-INSPECT`: el bug de redacción de Next.js también afecta al flujo de **documentos**. Aplica el mismo fix return-based ya validado en `aprobadas/actions.ts` (FB-F4-14) y en ausencia/pasaje (FB-F4-16).
> **App-only, sin migración.** Fix de lógica (cambia el contrato de las actions) → requiere auditoría (`FB-F4-AUD-13`). Va en branch nueva desde `main`.

---

## 1. Objetivo

En producción, los mensajes amigables es-AR del flujo de documentos se veían redactados/genéricos porque las actions hacían `throw new Error(mensajeAmigable)` cruzando el límite de una Server Action. Convertidas al contrato **`{ ok: true, ... } | { ok: false, error }`**, idéntico al ya validado.

---

## 2. Alcance implementado

### 2.1 Actions convertidas (contrato return-based)

- **`app/(app)/aprobaciones/actions.ts`**: nuevo tipo `DocumentActionResult = { ok: true } | { ok: false; error: string }`. `approveDocument`: el `throw new Error(error.message)` del update pasa a `return { ok: false, error: error.message }`. `rejectDocument`: el `throw` de `motivoRequerido` y el de `error.message` del update pasan a `return`. El audit log (try/catch no bloqueante) y la notificación por email (try/catch no bloqueante, con su `throw` interno que nunca cruza el límite) quedan intactos — mismo criterio que FB-F4-16.
- **`app/(app)/mi-perfil/actions.ts`**: nuevo tipo `DocumentUploadResult = { ok: true } | { ok: false; error: string }`. `handleDocumentUpload` y `uploadDocumentForEmployee`: los `throw` de `archivoRequerido`, `tipoNoPermitido`, `certificadoTipoRequerido`, `descripcionRequerida`, `descripcionMaxima` y el `error.message` del insert pasan a `return`.
  - **Extensión de alcance, no pedida literalmente pero necesaria para cerrar el bug de verdad:** ambas actions también invocan `validateDocumentFile` (`lib/storage.ts`) y `storageUpload` (`lib/storage.ts::uploadDocument`), que **también tiran** `throw new Error(...)` con mensajes amigables (`archivoDemasiadoGrande`, `tipoArchivoNoPermitido`, y el `error.message` de Storage) y cuyo `throw` no estaba atrapado — cruzaba el límite de la Server Action igual que los demás. Envueltas en `try/catch` puntuales que devuelven `{ ok: false, error: err.message }`. Sin tocar `lib/storage.ts` (sigue siendo un helper que tira; eso es correcto, lo que cambió es que quien lo llama ya no deja que ese throw escape sin traducir).

### 2.2 Call sites adaptados

- **`AprobacionesTable.tsx`**: la rama `documento` de `handleApprove`/`handleRejectConfirm` (antes con `try/catch` sin chequeo) pasa a `const result = await approve/rejectDocument(...); if (!result.ok) { setActionError(result.error); return; }` — mismo patrón que las ramas `pasaje`/`ausencia` (ya convertidas en FB-F4-16). El `try/catch` externo se mantiene para errores inesperados (ej. sesión expirada en `requireAdmin()`).
- **`DocumentUploadModal.tsx`**: `handleSubmit` — `try/catch` con `err.message` reemplazado por `const result = await handleDocumentUpload(formData); if (!result.ok) { setError(result.error); return; } handleClose();`.
- **`AdminDocumentUploadModal.tsx`**: mismo patrón con `uploadDocumentForEmployee`.

**Ningún error tragado:** en los 3 call sites, `!ok` siempre setea el error visible y corta el flujo antes de asumir éxito (o cerrar el modal).

### 2.3 Decisión sobre `getSignedUrls` / `searchEmployees`

**Dejadas sin tocar.** Ambas tiran, pero con `copy.errors.generic` (mensaje ya genérico) — no hay un mensaje amigable específico que se pierda con la redacción; el usuario vería el mismo texto genérico esté o no redactado. Consistente con la decisión explícita del propio alcance de esta pieza (no bloqueante, opcional).

## 3. Tests

**Unit/RTL nuevos** (`tests/unit/document-actions-error-visibility.test.tsx`), uno por call site, cada uno mockea la action a `{ok:false, error}` y ejerce una interacción real (click/submit):
- `AprobacionesTable` (kind `documento`): `approveDocument` → `{ok:false}` → el error se renderiza, `resolvedEmailFailed` no aparece.
- `DocumentUploadModal`: `handleDocumentUpload` → `{ok:false, error: tipoArchivoNoPermitido + mime}` → el error se renderiza, `onClose` NO se llama (el éxito cierra el modal, el error no).
- `AdminDocumentUploadModal`: `uploadDocumentForEmployee` → `{ok:false, error: archivoDemasiadoGrande}` → mismo patrón.

**Verificación de que no son mocks triviales:** se sabotearon temporalmente los tres call sites (se les quitó el `if (!result.ok) {...}`, dejándolos asumir éxito) y se corrió cada test — los tres fallaron (`waitFor` con timeout, el texto del error nunca apareció). Se restauraron los tres archivos inmediatamente después, confirmado sin diff contra el estado con el fix aplicado.

**Test existente actualizado** (`tests/unit/document-rejection-email.test.ts`): los `resolves.toBeUndefined()` de `rejectDocument` pasan a `resolves.toEqual({ ok: true })`; el caso "rechaza el motivo vacío" pasa de `.rejects.toThrow()` a `.resolves.toEqual({ ok: false, error: copy.aprobaciones.rejectModal.motivoRequired })`. `aprobaciones-overwrite-aviso.test.tsx`/`aprobaciones-saldo-badge.test.tsx` no requirieron cambios: mockean `approveDocument`/`rejectDocument` pero nunca disparan un click de aprobar/rechazar sobre un item `documento` (confirmado antes de decidir que no hacía falta tocarlos).

**e2e (build de producción real)** — `tests/e2e/documentos.spec.ts` (nuevo): sube un archivo `.txt` (MIME no permitido) por el formulario real de `/mi-perfil` y verifica que aparece `copy.documentos.errors.tipoArchivoNoPermitido`, no el texto genérico redactado de Next, y que el modal sigue abierto. Se eligió este caso (no "motivo vacío" en rechazo, que valida client-side antes de tocar el servidor, ni "tipo de documento no permitido", que exige un valor fuera de las opciones del `<Select>` y no es alcanzable por UI real) porque es el único error del flujo de documentos genuinamente disparable por un usuario real sin manipular el DOM: el atributo `accept` del `<input type="file">` es solo un filtro de UI, no una validación de constraint — Playwright puede adjuntar un `.txt` igual que un usuario podría vía "todos los archivos" en el diálogo nativo, y la validación real corre server-side.
