# FB-F4-16 — Fix: mensajes de error amigables en producción para las actions de resolución (Pieza 1/2)

> **Fase 4 · Cierre · Fix.** Para Claude Code, vía Luciano.
> Corrige el bug de redacción de Next.js (documentado en `FB-F4-14 §8`) en las actions de resolución de ausencia y pasaje, aplicando el **mismo contrato return-based** ya validado en `app/(app)/aprobadas/actions.ts` (FB-F4-14).
> **App-only, sin migración.** Es un **fix de lógica** (cambia el contrato de las actions) → **requiere auditoría** (`FB-F4-AUD-12`). Va en **branch nueva desde `main`** (no es corrección de un PR abierto; es un bug ya en prod).

---

## 1. Objetivo

En producción, Next.js **redacta** el mensaje de cualquier `Error` que cruce el límite de una Server Action → el patrón `throw new Error(mensajeAmigable)` muestra un error genérico en vez del mensaje en español. Las actions de resolución de **Pieza 1/2** seguían usando ese patrón, así que en prod el usuario veía errores redactados en flujos ya en uso.

Aplicado el contrato **return-based** (`{ ok: true, ... } | { ok: false, error }`) — el mismo fix ya validado en `aprobadas/actions.ts` — a esas actions, para que el mensaje amigable sobreviva a producción.

---

## 2. Inspección previa (reutilizar el patrón ya validado) — reportado

1. **`app/(app)/aprobadas/actions.ts`** (FB-F4-14): contrato de referencia — `{ ok: true, emailSent } | { ok: false, error }`, sin `throw` para ningún error esperado/traducido; los call sites (`AprobadasTable.tsx`) chequean `!result.ok` antes de mostrar éxito. Replicado tal cual, sin inventar un contrato nuevo.
2. **Mapeo de actions y call sites** — acá surgió una ambigüedad real de alcance (resuelta con Luciano antes de tocar código, ver §2.1) que **amplió el alcance a 4 archivos**, no 2:
   - `app/(app)/aprobaciones/ausencia-actions.ts` (`approveAusencia`, `rejectAusencia`) → call site: `AprobacionesTable.tsx`.
   - `app/(app)/aprobaciones/pasaje-actions.ts` (`approvePasaje`, `rejectPasaje`) → call site: `AprobacionesTable.tsx`.
   - `app/(app)/solicitud-ausencia/actions.ts` (`createAusenciaRequest`) → call site: `SolicitudAusenciaForm.tsx`.
   - `app/(app)/solicitud-pasaje/actions.ts` (`createPasajeRequest`) → call site: `SolicitudPasajeForm.tsx`.
3. **Traducciones de error existentes** confirmadas ya amigables, solo había que devolverlas en vez de tirarlas: `translateResolverAusenciaError` ("ya fue resuelta"), `translateAusenciaInsertError` (solapamiento `23P01` → `pendienteDuplicada`), `copy.aprobaciones.rejectModal.motivoRequired`, `copy.solicitudPasaje.errors.empleadoRequerido`/`empleadoFueraDeEquipo`, `copy.errors.unauthorized`/`generic`, y el resultado de `validateAusenciaRequestInput`/`validatePasajeRequestInput`.

### 2.1 Ambigüedad de alcance (resuelta con Luciano antes de tocar código)

El prompt nombraba literalmente solo `aprobaciones/ausencia-actions.ts` y `pasaje-actions.ts` (§2 punto 2, §3 primer bullet) — coincide con los ÚNICOS DOS archivos del repo con ese nombre exacto. Pero el DoD pedía tests de "solapamiento `23P01`" y "scope inválido", errores que **no ocurren en aprobar/rechazar** (la RPC de resolución no valida solapamiento ni scope — eso vive en el INSERT de creación). Esos casos solo existen en `solicitud-ausencia/actions.ts` y `solicitud-pasaje/actions.ts` (archivos llamados `actions.ts`, no `*-actions.ts` — no coinciden con el nombre literal del alcance). Contradicción real entre el texto del alcance y los casos de test pedidos, no una interpretación laxa.

Se preguntó explícitamente y Luciano confirmó: **las 4 actions**, no solo las 2 nombradas literalmente — cierra el mismo bug donde realmente aparecen los casos que pide el DoD.

## 3. Alcance implementado

### 3.1 Actions convertidas (contrato return-based)

- **`ausencia-actions.ts`**: `ResolveAusenciaResult = { ok: true; emailSent: boolean } | { ok: false; error: string }`. `assertPendiente` (throw) → `isPendiente` (boolean). Los 3 puntos de `throw` de cada función (`rejectModal.motivoRequired`, `alreadyResolved`, `translateResolverAusenciaError`/`errors.generic`) pasan a `return { ok: false, error }`.
- **`pasaje-actions.ts`**: mismo patrón, mismo tipo `ResolvePasajeResult`.
- **`solicitud-ausencia/actions.ts`**: `CreateAusenciaResult = { ok: true } | { ok: false; error: string }`. Los 3 puntos de `throw` (`errors.unauthorized`, `validateAusenciaRequestInput`, `translateAusenciaInsertError`/`errors.generic`) pasan a `return`.
- **`solicitud-pasaje/actions.ts`**: `CreatePasajeResult = { ok: true } | { ok: false; error: string }`. Los 5 puntos de `throw` (`unauthorized`, `empleadoRequerido`, `memberError`→`generic`, `empleadoFueraDeEquipo`, `validatePasajeRequestInput`, insert error→`generic`) pasan a `return`.

**Distinción errores esperados vs. inesperados (no se convirtió todo indiscriminadamente):** el único `throw` que queda en los 4 archivos es el interno de `fetchRequestForNotification` (`ausencia-actions.ts`/`pasaje-actions.ts`) — nunca cruza el límite de la Server Action: está envuelto en su propio `try/catch` (mail best-effort) DENTRO de la misma función, así que nunca llega redactado al cliente. No se tocó porque no es el bug — es la razón por la que sigue siendo un `throw` legítimo. `approveDocument`/`rejectDocument` (`aprobaciones/actions.ts`, documentos) también quedaron sin tocar — mismo patrón/bug latente, pero fuera de alcance explícito de esta pieza (documentos, no ausencia/pasaje); documentado, no arreglado.

### 3.2 Call sites adaptados

- **`AprobacionesTable.tsx`**: `handleApprove`/`handleRejectConfirm` — las ramas `pasaje`/`ausencia` chequean `!result.ok` (muestran `result.error` y `return`) antes de revisar `emailSent`. La rama `documento` (`approveDocument`/`rejectDocument`) sigue con `try/catch` sin cambios — no forma parte del alcance.
- **`SolicitudAusenciaForm.tsx`**: `handleSubmit` — `const result = await createAusenciaRequest(...)`, `if (!result.ok) { setError(result.error); return; }`.
- **`SolicitudPasajeForm.tsx`**: mismo patrón (`submitResult`, para no chocar con el `result` de la validación de cliente que ya existía en el mismo scope).

**Ningún error tragado:** en los 3 call sites, la rama `!ok` siempre setea el estado de error visible (`setActionError`/`setError`) y corta el flujo (`return`) antes de asumir éxito.

## 4. Tests

**Unitarios actualizados** (sin agregar cobertura nueva de comportamiento — el comportamiento no cambió, solo cómo se comunica — 123 tests entre los 7 archivos afectados, todos verdes):
- `tests/unit/aprobaciones-ausencia.test.ts` / `aprobaciones-pasaje.test.ts`: los 6+6 `.rejects.toThrow(...)` pasaron a `.resolves.toEqual({ ok: false, error: ... })`; los `toEqual({ emailSent })` pasaron a `toEqual({ ok: true, emailSent })`.
- `tests/unit/solicitud-ausencia.test.ts`: 9 casos `.rejects.toThrow` → `.resolves.toEqual({ ok: false, error })` (incluido el de solapamiento `23P01`).
- `tests/unit/solicitud-pasaje.test.ts`: 10 casos ídem (incluido scope inválido, no-retroactiva).
- `tests/unit/solicitud-ausencia-form.test.tsx`: el mock de `createAusenciaRequest` pasó de `mockResolvedValue(undefined)` a `mockResolvedValue({ ok: true })` (con `undefined`, `result.ok` explotaría con el código nuevo).
- `tests/unit/aprobaciones-overwrite-aviso.test.tsx` / `aprobaciones-saldo-badge.test.tsx`: sin cambios — nunca disparan los mocks de aprobar/rechazar (solo verifican presencia/estado de los botones), confirmado antes de decidir que no hacía falta tocarlos.

**e2e (build de producción real — el caso que expuso el bug):** `tests/e2e/solicitudes.spec.ts`, test nuevo `solapamiento con una pendiente existente muestra el mensaje amigable, no el genérico redactado` — siembra una ausencia pendiente para el mismo empleado/fecha, envía el formulario real por UI con la misma fecha, y verifica que aparece `copy.solicitudAusencia.errors.pendienteDuplicada` (no `"An error occurred in the Server Components render..."`). Se eligió el caso de solapamiento (no "rechazar sin motivo", que valida client-side antes de tocar el servidor) porque es el único que **de verdad** ejercita el límite de la Server Action con un error server-side — el caso que solo se puede probar contra `next build && next start` (exactamente lo que corre este job), nunca contra `next dev` ni un test unitario con mocks.
