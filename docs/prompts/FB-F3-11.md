# FB-F3-11 — Secciones colapsables + filtro por empleado en el módulo Calendario

> **Fase:** 3 — Calendario de Rotaciones
> **Tipo:** Build (ajuste de UI; sin cambio de esquema ni de datos)
> **Constitución vigente:** v0.5 (`docs/constitucion.md`) · **PRD:** `docs/prd-fase-3.md`
> **Estado de partida:** módulo `/calendario` en `main` con tres secciones apiladas: panel de alertas de franco, dashboard de motivos de ausencia (resumen del mes) y la grilla del calendario.

---

## Objetivo

Mejorar la legibilidad del módulo `/calendario` cuando hay muchos empleados, con dos capacidades:

1. **Colapsar/expandir** cada una de las tres secciones individualmente (preferencia recordada entre visitas).
2. **Filtrar por empleado** (selección múltiple) aplicando el filtro a las tres secciones a la vez (el filtro NO se recuerda: siempre arranca sin filtro).

Es solo presentación y filtrado en cliente/servidor sobre datos ya autorizados. **No** cambia datos, cálculo, scope de seguridad, esquema ni RLS.

---

## Alcance

### A) Secciones colapsables (las tres, individualmente)
Las tres secciones que hoy se apilan en `/calendario`:
1. **Alertas de franco** (`FrancoAlertPanel`).
2. **Resumen de ausencias del mes** (dashboard de motivos, `MotivoDashboard`).
3. **Calendario** (la grilla, `RosterGrid` + `MonthNav` + `Legend`).

Cada una:
- Tiene un **encabezado clickeable** que expande/colapsa esa sección (chevron o indicador de estado claro).
- **Colapsada** muestra solo el encabezado (título). Donde tenga sentido, incluir un **contador** en el título:
  - Alertas de franco → cantidad de empleados en alerta (ej. "Alertas de franco (2)").
  - Resumen de ausencias y Calendario → sin contador obligatorio (título solo).
- Es accesible: el encabezado es un control operable por teclado (`button` / `aria-expanded`), no un `div` con `onClick` suelto.

**Estado por defecto (primera visita, sin preferencia guardada):**
- **Calendario: expandido.**
- **Alertas de franco: colapsada.**
- **Resumen de ausencias: colapsado.**

Este default aplica **solo** cuando todavía no hay preferencia guardada.

**Persistencia de la preferencia de colapsado:**
- El estado colapsado/expandido de cada sección **se recuerda entre visitas**.
- Implementar con **cookie** (legible en el server component de la ruta, aplicada en el render inicial para evitar parpadeo). **No** usar `localStorage` (no es el patrón de este stack) ni base (sería un cambio de esquema innecesario para una preferencia cosmética).
- Al cambiar el estado de una sección, se actualiza la cookie; la próxima visita respeta lo último que dejó el usuario. El default solo se usa si la cookie no existe.
- La cookie guarda solo la preferencia de UI. Sin datos sensibles.

### B) Filtro por empleado (selección múltiple)
- Un control de **selección múltiple de empleados** (ej. multiselect / chips con checkboxes) que permite elegir uno o varios empleados.
- El filtro **aplica a las tres secciones a la vez**: alertas de franco, resumen de ausencias y calendario se acotan al conjunto de empleados seleccionados.
- **Sin selección = todos** los empleados visibles (comportamiento actual).
- El filtro **NO se persiste**: al salir y volver a `/calendario`, arranca **sin filtro** (todos), independientemente de lo que se haya filtrado antes. (A diferencia del colapsado, que sí se recuerda.)
- La lista de empleados elegibles en el filtro es **exactamente el scope del rol** ya resuelto (ver seguridad): el admin filtra entre todos; el supervisor solo entre su equipo + sí mismo; el empleado no necesita filtro (ve solo su fila) — para empleado el control puede omitirse.
- El filtro es un **acotamiento de presentación** dentro de lo que el rol ya puede ver; **nunca** amplía el scope ni permite ver empleados fuera del alcance del rol.

---

## Datos / RLS / Seguridad

- **Sin cambios de esquema, datos, cálculo, scope de seguridad ni RLS.** Es presentación + una cookie de preferencia de colapsado + filtrado en runtime.
- El **filtro por empleado opera sobre el conjunto ya autorizado** por el scope de rol existente (admin todos / supervisor equipo + sí mismo / empleado propio). No se consulta ni se muestra ningún empleado fuera de ese conjunto. Si el filtrado se hace en servidor, la query base sigue acotada por el scope de rol y el filtro solo restringe dentro de él; si se hace en cliente, se filtra sobre datos ya acotados por el servidor.
- La cookie de colapsado no reemplaza ningún control de acceso.
- Copy es-AR en `/lib/copy` (títulos de sección, textos de contador, label del filtro). Sin secretos.

## Tests

- **Colapsable:** clickear el encabezado alterna expandido/colapsado; colapsada, el contenido no se renderiza (u oculto de forma accesible); expandida, sí.
- **Default sin cookie:** primera visita → calendario expandido, alertas y resumen colapsados.
- **Persistencia de colapsado:** con una cookie que marca (ej.) alertas expandida y calendario colapsado, el render inicial respeta esa preferencia por sobre el default.
- **Accesibilidad:** encabezado con `aria-expanded` correcto y operable por teclado.
- **Filtro por empleado:** seleccionar un subconjunto acota las tres secciones a esos empleados; sin selección = todos; la selección incluye solo empleados del scope del rol.
- **Filtro NO persiste:** tras "salir y volver" (nueva carga sin estado de filtro), arranca sin filtro aunque antes se hubiera filtrado.
- **Rol:** para empleado no se renderiza la sección de alertas (regresión de FB-F3-09) y el filtro no expone empleados fuera de su scope (para empleado, sin filtro relevante).
- Todo verde en CI.
