# FB-F1-10 — Fix del seed de mi-perfil.test.ts (datos no visibles contra Supabase real)

- **ID:** FB-F1-10
- **Fecha:** 19 de junio de 2026
- **Destino:** Claude Code
- **Propósito:** Que el seed de `mi-perfil.test.ts` deje sus filas presentes/visibles para sus tests. No tocar app, migraciones ni policies.

## Contexto

Con la suite corriendo contra Supabase real (FB-F1-07 a FB-F1-09), `rls.test.ts`, `purge.test.ts` y `migration.test.ts` pasaban. Las únicas 10 fallas estaban en `mi-perfil.test.ts`:

- `INSERT INTO documents` → viola `documents_user_id_fkey` ("Key is not present in table profiles")
- `SELECT` de perfil/documento propio → 0 filas
- `UPDATE` de admin → 0 filas afectadas

## Causa raíz

`setupTestDb()` dependía del trigger `on_auth_user_created` (migración 0001) para crear los perfiles después de insertar en `auth.users`. Si el trigger no disparaba (o lo hacía con los valores por defecto de `'empleado'`), el paso posterior de corrección era un `UPDATE ... WHERE p.id = v.id` que actualizaba 0 filas silenciosamente — ningún error, pero profiles vacío.

`mi-perfil.test.ts` es el primer archivo en correr (orden alfabético). En un DB recién inicializado por `supabase start`, el trigger falla silenciosamente o no aplica en el contexto de inserción directa en `auth.users` como superusuario. Los archivos que corrían después (`purge.test.ts`, `rls.test.ts`) se beneficiaban de los profiles ya creados en la DB por runs anteriores.

## Cambio implementado

**`tests/integration/helpers.ts`** — `setupTestDb()`, paso 5:

Reemplazado el `UPDATE profiles FROM (VALUES ...) WHERE p.id = v.id` por un `INSERT INTO public.profiles ... ON CONFLICT (id) DO UPDATE SET ...` que siembra perfiles directamente, sin depender del trigger.

```sql
INSERT INTO public.profiles (id, email, full_name, role, status) VALUES
  ($1::uuid, 'admin@test.com',       'Admin Test',       'admin'::user_role,      'activo'::employee_status),
  ($2::uuid, 'supervisor@test.com',  'Supervisor Test',  'supervisor'::user_role, 'activo'::employee_status),
  ($3::uuid, 'supervisor2@test.com', 'Supervisor2 Test', 'supervisor'::user_role, 'activo'::employee_status),
  ($4::uuid, 'emp1@test.com',        'Empleado 1',       'empleado'::user_role,   'activo'::employee_status),
  ($5::uuid, 'emp2@test.com',        'Empleado 2',       'empleado'::user_role,   'activo'::employee_status),
  ($6::uuid, 'emp3@test.com',        'Empleado 3',       'empleado'::user_role,   'activo'::employee_status)
ON CONFLICT (id) DO UPDATE SET
  email     = EXCLUDED.email,
  full_name = EXCLUDED.full_name,
  role      = EXCLUDED.role,
  status    = EXCLUDED.status
```

El INSERT en `auth.users` se conserva (necesario para la FK `profiles.id REFERENCES auth.users(id)` y para el entorno realista de auth). El paso 6 de `supervisor_id` no cambia.

### Por qué funciona

- El cliente de `setupTestDb()` conecta como `postgres` (superusuario) → bypassa RLS en `profiles`.
- `ON CONFLICT (id) DO UPDATE` cubre tres escenarios: trigger no disparó (INSERT crea el perfil), trigger disparó con valores por defecto (UPDATE los corrige), segunda llamada de `setupTestDb()` en la misma sesión (UPDATE idempotente).
- El INSERT directo es determinístico y no depende del comportamiento del trigger en el entorno real.
