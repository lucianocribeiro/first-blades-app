## 3. Alcance

### 3.1 Formulario unificado
- Un solo "Solicitud de Ausencia" con:
  - Desplegable **motivo** (`vacaciones`, `licencia_medica`, `dia_tramite`, `matrimonio`, `fallecimiento`, `otros`) — copy amigable en es-AR (nada de nombres de enum a la vista).
  - Rango `fecha_inicio` / `fecha_fin` (para un día puntual, inicio = fin).
  - `motivo_otros_texto` (máx 80, espejo de la columna) **visible sólo si motivo = `otros`**, requerido en ese caso.
  - **Saldo de día de trámite** (restantes = 3 − consumidos) mostrado **sólo** cuando el motivo elegido es `dia_tramite`, reutilizando la lógica existente. Alerta de saldo excedido **no bloqueante** (ya construida) — se conserva.
- **Día de trámite queda absorbido** como una opción más; retirar el formulario standalone y redirigir/migrar su ruta a la unificada. Sin duplicar lógica.
- Empleado y Supervisor envían **para sí** (la solicitud de pasaje para el equipo es otra pieza). Estado inicial `pendiente` (policy `ausencias_insert_non_admin`); nada se autoactiva.

### 3.2 No-retroactiva (server-side, todos los motivos)
- En la **action de creación**, revalidar `fecha_inicio >= getBusinessToday()` (zona `America/Argentina/Buenos_Aires`; **hoy permitido**). Rechazo con copy amigable es-AR si es retroactiva. Además, validar `fecha_fin >= fecha_inicio`.
- Es validación de negocio en la capa de app (mismo precedente que el scope de motivo); no va como CHECK en DB (`CURRENT_DATE` no es inmutable).
- El cliente puede pre-validar para UX, pero **la autoridad es server-side**.

### 3.3 Error de solapamiento (ya en DB) → copy amigable
- La exclusion constraint `ausencia_requests_no_solapamiento_pendiente` (0014) emite `23P01`. `translateAusenciaInsertError` ya mapea ese código: confirmar que el copy es-AR es claro para cualquier motivo (ej. "Ya tenés una solicitud pendiente que se superpone con estas fechas. Resolvela antes de pedir otra."). Generalizar el texto si hoy asume día de trámite.

### 3.4 Generalizar la revalidación de scope de la resolución
- En la **action de resolución**, ampliar la guarda server-side de `estado='pendiente'` + `motivo_ausencia='dia_tramite'` a `estado='pendiente'` + **cualquier motivo**. Mantener la re-lectura de la solicitud antes de invocar la RPC (no confiar sólo en el parámetro).
- La RLS y la guarda de la RPC no limitan el motivo por diseño — el scope lo pone la action. Ahora el scope correcto es "cualquier ausencia pendiente".

### 3.5 Cola de Aprobaciones — todos los motivos
- Ampliar el filtro para traer ausencias `pendiente` de **todos los motivos** (no sólo `dia_tramite`). Cada ítem muestra motivo (copy amigable), empleado, rango, y `motivo_otros_texto` si aplica.
- Mantener la bandeja **única** (pasajes, ausencias, documentos, onboarding conviven); esta pieza sólo amplía el segmento de ausencias.

### 3.6 Alerta de sobrescritura (no bloqueante)
- Al abrir una ausencia pendiente para resolver, el server calcula y devuelve los **días del rango que ya tienen fila** en `rotation_assignments` (`fecha` entre `fecha_inicio..fecha_fin` para ese `user_id`) — **cualquier fila cuenta, incluidos `es_estimado=true`**.
- La UI lista esos días con su **estado actual** y una marca si es **estimado**, con un texto no bloqueante del tipo "Al aprobar, estos días se sobrescriben a período fuera de trabajo." La aprobación sigue siendo un click; el aviso **sólo informa**.
- Lectura con `createServerClient()` (RLS: admin ve todo el calendario); filtro de app explícito por `user_id` + rango.
- **Best-effort informativo:** es una previsualización del estado actual; la escritura real y el registro de `old_data` los hace la RPC atómica al aprobar. No introducir un lock ni bloquear por diferencias entre la previsualización y el momento de aprobar (no over-engineering).

## 5. Tests

**Unit / componente:**
- El formulario muestra `motivo_otros_texto` sólo con `otros` y lo exige; muestra el saldo sólo con `dia_tramite`.
- Pre-validación de rango (`fecha_fin >= fecha_inicio`) y de no-retroactiva en cliente (UX), sabiendo que la autoridad es server-side.

**Integración (bajo JWT de rol `asUser`; hard-fail si no puede correr):**
- **No-retroactiva:** la action rechaza `fecha_inicio < hoy` para todos los motivos; acepta `fecha_inicio = hoy`.
- **Solapamiento:** insertar una pendiente que se superpone con otra pendiente del mismo empleado → error traducido a copy amigable (`23P01`), cualquier motivo.
- **Scope de resolución generalizado:** aprobar/rechazar funciona para un motivo ≠ `dia_tramite` (antes bloqueado por la guarda hardcodeada); una solicitud ya resuelta no se re-resuelve.
- **Cola de Aprobaciones:** trae ausencias `pendiente` de todos los motivos, no sólo `dia_tramite`.
- **Sobrescritura (previsualización):** para un rango con días ya asignados (incluido un día `es_estimado=true`), el server devuelve exactamente esos días con su estado; un rango totalmente libre no reporta días.
- **Saldo de día de trámite** intacto: sigue contando `dia_tramite` (incl. estimados) y mostrando restantes; no afectado por la unificación.
- **Regresión:** el flujo de día de trámite existente sigue funcionando end-to-end desde el formulario unificado.

**CI:** typecheck / lint / build + integración RLS real corrida de verdad (no skip).
