## Hallazgo 1 — Filtro de aplicación en el detalle

**Estado real:** la RLS **ya bloquea** que un no-admin abra un archivado por URL directa. No hay exposición hoy. Lo que falta es la capa de aplicación que el prompt pedía superpuesta, para que el módulo no quede dependiendo de una sola línea de defensa.

**Qué hacer** (`app/(app)/procedimientos/[id]/page.tsx:24`):

1. Agregá el filtro explícito: no-admin consulta con `estado = 'vigente'`; el admin consulta ambos estados.
2. Que el resultado vacío se traduzca en un "no encontrado" limpio, **sin filtrar por el mensaje** si el procedimiento existe pero está archivado. Que no se pueda deducir su existencia.
3. **Comentá en el código** que el filtro es una segunda capa deliberada sobre la RLS, no la defensa principal. Sin eso, el próximo que lo lea lo va a borrar por redundante.

**Tests:** e2e de URL directa a un archivado, como Empleado y como Supervisor. Ambos ven "no encontrado". Y el admin sí lo ve.

## Hallazgo 2 — `file_path` serializado al cliente

**Estado real:** el bucket es privado y la ruta sola no da acceso a nada. Es higiene, no una filtración.

**Qué hacer** (`app/(app)/procedimientos/[id]/editar/page.tsx:50` y `ProcedimientoForm.tsx:13`):

Pasá al componente cliente un booleano o un enum (`tipoContenidoInicial`), nunca el `file_path` real. El path se queda del lado del servidor. Revisá que no viaje por otro camino en el mismo formulario.

## Hallazgo 3 — `requireAdmin()` y el contrato return-based

**Decisión tomada: el `redirect` se queda. Se documenta como excepción intencional.**

Razones, para que queden en el código:

- El contrato return-based existe porque Next **redacta en producción** el mensaje de un `Error` que cruza el límite de una Server Action. `redirect()` no es eso: Next lo maneja con un mecanismo propio que funciona igual en producción.
- Un no-admin llamando a estas acciones no es un error que haya que explicarle: es alguien fuera de lugar. Redirigirlo es la respuesta correcta, y además no le confirma qué existe del otro lado.
- Cambiar `requireAdmin()`, que es un helper compartido, arrastraría a todos sus call sites por una prolijidad.

**Qué hacer:**

1. **No toques `lib/auth.ts`** ni el comportamiento de `requireAdmin()`.
2. Documentá la excepción **en el código**, arriba de las tres actions (`actions.ts:46`, `:106`, `:204`): que el guard de rol corta por `redirect` y que el contrato `{ ok }` aplica a los errores de negocio de una llamada legítima.
3. Ajustá los tests para que la aserción sea explícita: el `redirect` **es** el comportamiento esperado ante un no-admin, no un vacío de cobertura.
4. Agregá esta excepción a `docs/constitucion.md` como nota del §2.5: el contrato aplica a errores esperados de una llamada autorizada; los guards de rol cortan por `redirect`. Redactala corta y ubicala donde corresponda.

## Hallazgo 4 — e2e del flujo real de subida

**Se agrega.** El precedente de Fase 4 pesa: el bug de redacción de Next era invisible en dev y en tests mockeados, y solo lo cazó un e2e contra build de producción. Un cruce `File` → Server Action → Storage → signed URL tiene esa misma forma.

**Qué hacer** (`tests/e2e/procedimientos.spec.ts`):

Un recorrido de admin, con un archivo **chico de verdad** (un `.txt` de unos pocos bytes, no un PDF de muestra):

1. Crear un procedimiento con archivo.
2. Abrir el detalle y confirmar que el link firmado funciona.
3. Editar reemplazando el archivo, y confirmar que el anterior se borró del bucket.
4. Limpieza de datos al final del test.

Restricciones:

- **El job de e2e ya está lento (~13 min) y hay un ítem abierto para estabilizarlo.** Un test, chico, sin esperas artificiales. No agregues más recorridos de los pedidos.
- Recordá `storage.protect_delete()`: la limpieza tiene que usar la API real de Storage con clientes autenticados por rol, no SQL directo.
- Si el test sale inestable en CI, **no lo marques como skip ni le pongas reintentos para que pase.** Reportá y lo evaluamos.
