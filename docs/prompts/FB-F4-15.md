## 1. Objetivo

En "Mis solicitudes" de **pasaje**, el empleado **viajero** (`empleado_id`) no veía la marca post-aprobación (`post_aprobacion_tipo` / comentario / timestamp) cuando el pasaje lo pidió **otra persona** (un supervisor), porque la lista filtraba solo por `solicitante_id = profile.id`. Recibía el **mail** del cambio pero no tenía **representación in-app** — violaba el principio §2.4 (todo lo que dispara un mail tiene representación consultable in-app).

Corregido: el empleado viajero ve sus pasajes (y su marca post-aprobación) aunque no haya sido el solicitante.

**Alcance:** solo pasaje. Las ausencias son siempre propias (solicitante = empleado) — no se tocó ese flujo.

---

## 2. Fix — query (verbatim, `app/(app)/solicitud-pasaje/page.tsx`)

Antes:
```ts
const { data, error } = await supabase
  .from('pasaje_requests')
  .select('*, empleado_profile:profiles!pasaje_requests_empleado_id_fkey(full_name, email)')
  .eq('solicitante_id', profile.id)
  .order('created_at', { ascending: false });
```

Después:
```ts
const { data, error } = await supabase
  .from('pasaje_requests')
  .select(
    '*, empleado_profile:profiles!pasaje_requests_empleado_id_fkey(full_name, email), solicitante_profile:profiles!pasaje_requests_solicitante_id_fkey(full_name, email)'
  )
  .or(`solicitante_id.eq.${profile.id},empleado_id.eq.${profile.id}`)
  .order('created_at', { ascending: false });
```

- La RLS (`policy pasajes_select`) ya permite `empleado_id = auth.uid()` seleccionar la fila — ampliar la query no elude nada, solo deja de filtrar de más del lado de la app.
- **Dedup:** un solo `.or()` sobre una tabla no duplica filas (no es una `UNION` de dos queries) — cuando `solicitante_id = empleado_id = profile.id`, la fila sigue apareciendo una sola vez. No hizo falta dedup explícito en JS.
- Se sumó el join a `solicitante_profile` (mismo FK que ya usan `aprobaciones/page.tsx` y `aprobadas/page.tsx`) para poder mostrar quién pidió el pasaje cuando el viewer es el viajero, no el solicitante.
- `MisSolicitudesPasajeTable` ahora recibe `viewerId={profile.id}` para saber desde qué perspectiva renderizar cada fila.

## 3. Fix — copy ("Para quién" / "Pedido por")

`lib/copy/index.ts`, sección `solicitudPasaje.detalle`:
```ts
detalle: {
  paraLabel:      'Para',
  pedidoPorLabel: 'Pedido por',
},
```

`MisSolicitudesPasajeTable.tsx` — la columna que antes era `empleadoLabel()` (solo mostraba a quién viaja, cuando distinto del solicitante) pasó a `paraQuienLabel(req, viewerId)`, con las **tres** perspectivas posibles sobre una misma fila:
- Viewer = solicitante, pidió para sí (`solicitante_id === empleado_id`): `—` (sin cambio de comportamiento).
- Viewer = solicitante, pidió para otro integrante de su equipo: `Para: <nombre del viajero>` (sin cambio de comportamiento).
- **Viewer ≠ solicitante** (viewer es el empleado viajero, otra persona — su supervisor — lo pidió): `Pedido por: <nombre del solicitante>` — **caso nuevo**, antes esta fila ni siquiera llegaba a la tabla.
