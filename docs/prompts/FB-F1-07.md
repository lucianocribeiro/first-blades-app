# FB-F1-07 — Tests de integración contra un Supabase real en CI

- **ID:** FB-F1-07
- **Fecha:** 19 de junio de 2026
- **Destino:** Claude Code
- **Propósito:** Reemplazar el Postgres plano de CI + el mock de Supabase por un Supabase local real levantado con la CLI. El cambio es de infraestructura de test; la lógica de app y las políticas RLS no se modifican.

## Contexto

La suite de integración corría contra `postgres:16` (imagen Docker oficial) con un mock manual de auth/storage en `tests/integration/setup.sql`. Este enfoque requería mantener el mock sincronizado con Supabase (triggers, funciones, roles) y era fuente continua de errores de infraestructura (42P13, 42P08, roles inexistentes).

## Cambios implementados

### (1) CI: levantar Supabase real

**`.github/workflows/ci.yml`:**
- Eliminado el service `postgres:16`.
- Agregados pasos `supabase/setup-cli@v1` + `supabase start` en el job `integration`.
- `TEST_DATABASE_URL` apunta a `postgresql://postgres:postgres@localhost:54322/postgres` (puerto de Supabase local).
- Ambos jobs: `node-version` actualizado de `'20'` a `'22'` (Node 20 EOL).

**`supabase/config.toml`** (archivo nuevo):
- Config mínima necesaria para que `supabase start` funcione.
- `[db] major_version = 15`, puerto 54322; studio e inbucket desactivados.

### (2) Retirar el mock

**`tests/integration/setup.sql`:**
- Archivo vaciado (conservado para referencia histórica).
- El stack real provee `auth.uid()`, `auth.role()`, `storage.foldername()`, `storage.objects`, roles `authenticated`/`service_role`/`anon`, y el trigger `on_auth_user_created`.

### (3) Conexión y contexto de rol

Los helpers `asUser` y `asServiceRole` no cambiaron: siguen usando `SET LOCAL ROLE authenticated` / `SET LOCAL ROLE service_role` + `request.jwt.claims`. Funciona igual en Supabase local porque `postgres` (superusuario) puede `SET ROLE` a cualquier rol sin necesitar membresía explícita.

### (4) Seed limpio y casteos UUID explícitos

**`tests/integration/helpers.ts`** — nuevo `setupTestDb()`:
- No droguea ni recrea esquemas auth/storage.
- `TRUNCATE` de todas las tablas públicas (`CASCADE`) + `DELETE FROM storage.objects WHERE bucket_id = 'documents'`.
- `DELETE FROM auth.users WHERE id = ANY(test_ids)` — elimina usuarios de test anteriores.
- `INSERT INTO auth.users` con schema completo de Supabase real (aud, role, encrypted_password, is_sso_user, is_anonymous…). El trigger `on_auth_user_created` crea los perfiles automáticamente.
- `UPDATE profiles` masivo vía `FROM (VALUES ...)` para corregir role/email/full_name (el trigger asigna role='empleado' por defecto).
- Quita `readFileSync`/`resolve` (ya no se leen setup.sql ni migraciones).

**`tests/integration/rls.test.ts`** — 5 casteos corregidos (error 42P08):
- `$n || '/ruta'` → `$n::text || '/ruta'`
- `$n` en columnas UUID → `$n::uuid`

**`tests/integration/mi-perfil.test.ts`** — 8 casteos corregidos (mismo patrón).

### (5) Migration test sin drops de esquema

**`tests/integration/migration.test.ts`:**
- Eliminados `DROP SCHEMA` de auth/storage y la aplicación manual de migraciones.
- `beforeAll` solo conecta (el esquema ya fue aplicado por `supabase start`).
- Los tests verifican el estado resultante del esquema (tablas, funciones, enums, políticas, bucket).

### (6) Confirmación en CI

El job `integration` en GitHub Actions:
1. Checkout + Node 22 + Supabase CLI
2. `npm ci`
3. `supabase start` → aplica todas las migraciones de `supabase/migrations/`
4. `npm run test:integration` → `global-setup.ts` conecta al puerto 54322, sets `INTEGRATION_DB_AVAILABLE=true`, tests corren sin skip

## Fuera de alcance

- Lógica de feature y policies de RLS: no se cambiaron para forzar verde.
- Seed de producción (`supabase/seed.ts`): no se modificó; es un script manual, no un `seed.sql` que `supabase start` ejecute automáticamente.
