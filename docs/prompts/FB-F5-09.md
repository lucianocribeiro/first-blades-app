## Hallazgo 1 — Mensajes del login

`app/login/LoginForm.tsx:36-38`, `app/login/page.tsx:14-18`

Hoy: credencial inválida muestra "Correo o contraseña incorrectos"; un usuario no `activo` con contraseña correcta muestra "Tu sesión expiró".

**Qué hacer:**

1. Un usuario que autentica bien pero **no está `activo`** tiene que ver **exactamente el mismo mensaje** que una credencial inválida. Indistinguible.
2. **Cuidado con no romper el caso legítimo:** un usuario `activo` cuya sesión venció de verdad **no** debería ver "correo o contraseña incorrectos", que sería confuso y falso. Distinguí los dos caminos: expiración real de sesión (sin sesión válida) puede conservar su copy neutro, porque no filtra nada; el rechazo por estado usa el copy de credencial inválida.
3. Ajustá el e2e (`tests/e2e/gestion-usuarios.spec.ts:97-104`), que hoy **fija la diferencia como expectativa** — el test está consagrando el problema. Que pase a verificar que los mensajes son indistinguibles.

## Hallazgo 2 — Errores de `audit_log` tragados

`gestion-usuarios/actions.ts:123-130`, `:159-166`, `:203-209`

El `try/catch` no captura el `{ error }` que PostgREST devuelve **como valor** cuando la query falla. O sea que una auditoría que falla no deja rastro en ningún lado.

**Qué hacer:**

1. Leé el resultado: `const { error: auditError } = await ...`. Si existe, `console.error` con contexto suficiente para saber qué operación fue y sobre quién.
2. **Mantenelo no bloqueante:** la operación principal sigue devolviendo `{ ok: true }`. Falla la auditoría, no la baja.
3. Ajustá el test (`gestion-usuarios-actions.test.ts:191-199`) para que además verifique que el error **quedó visible**, no solo que la operación siguió.
4. **No toques `aprobaciones/actions.ts`**, que tiene el mismo problema de origen. Es código preexistente fuera del alcance de esta fase y ya quedó registrado para resolver aparte.

## Hallazgo 3 — Hardening del usuario objetivo (bloqueante)

`gestion-usuarios/actions.ts:100-117`, `:139-155`, `:175-200`, `UserTable.tsx:85-122`

**Qué hacer:**

1. **Bloqueá que un admin se inactive a sí mismo.** Validación **del lado del server**, comparando contra el id de la sesión verificada. Mensaje claro en es-AR. Y ocultá o deshabilitá el botón "Desactivar" en su propia fila, con un tooltip que explique — la UI acompaña, el server decide.
2. **Releé el perfil objetivo del lado del server** después de `requireAdmin()`. Si no existe, rechazá con `{ ok: false }`. Hoy un id inexistente puede devolver `ok: true` y escribir una auditoría sobre un `record_id` que nunca existió.
3. **Verificá que el update afectó una fila.** Cero filas afectadas es un error, no un éxito silencioso.
4. Para `resetPassword`, confirmá que el usuario de Auth corresponde a un `profiles` gestionado por la app.

**Sobre inactivar a otro admin:** no lo bloquees. Es una operación legítima. El único caso irrecuperable es el de inactivarse a sí mismo.

**Tests:**

- Un admin no puede inactivarse a sí mismo: rechazado del lado del server.
- Un id inexistente devuelve `{ ok: false }` y **no** escribe en `audit_log`.
- Un admin sí puede inactivar a otro admin.
