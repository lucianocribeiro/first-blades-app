## Decisiones de producto (cerradas con Luciano — no re-abrir)

- **Una sola pantalla para todos.** El admin ve los botones de editar y archivar; los demás no. No hay pantalla de administración aparte.
- **Contenido: archivo *o* texto, nunca los dos.** La UI hace elegir uno.
  ⚠️ La base **acepta** que estén los dos (el CHECK pide "al menos uno"). La exclusividad la impone la aplicación. Es intencional: no vale la pena una migración nueva para esto con la tabla vacía. **Dejalo comentado en el código** para que el que lo lea después entienda que es a propósito.
- **Texto en Markdown**, con editor de negritas, listas y títulos. Se guarda Markdown, no HTML: no queda atado al editor y no arrastra el riesgo de HTML crudo.
- **Lista plana con filtro de categoría al costado.** No agrupada.
- **Categoría: texto libre con sugerencias** de las categorías ya usadas.
- **Badge "Nuevo" por 7 días** desde la publicación o la última actualización, igual para todos, sin acuse de lectura.
- **Archivado:** oculto para no-admin, visible para el admin con etiqueta, reversible.
- **Sin mail.** El aviso es in-app y nada más.

## Alcance

### 1. Pantalla de listado

Ruta del módulo (seguí la convención del shell y de `new-module`), visible para los tres roles.

- Lista plana: título, categoría, quién lo actualizó y cuándo, badge "Nuevo" si corresponde.
- **Búsqueda** por título y categoría. `ilike` **del lado del server**, no filtrado en el cliente. Sin `pg_trgm` — no está instalado y no hace falta.
- **Filtro de categoría** al costado, armado con las categorías realmente existentes.
- Para el admin: los archivados también, con etiqueta clara que los distinga, y un filtro para verlos o no. Para Supervisor y Empleado no existen: ni en la lista, ni en la búsqueda, ni por URL directa.
- **Estado vacío** con copy útil en es-AR, distinto según el rol (el admin puede crear, los demás no).

### 2. Ver un procedimiento

- Si es texto: Markdown renderizado. **Sanitizado sin excepción.** Nada de HTML crudo del contenido llegando al DOM sin pasar por el sanitizador, aunque el contenido lo escriba un admin.
- Si es archivo: apertura o descarga por **signed URL** generada en el server, contra el bucket `procedimientos`. Nunca una URL pública ni el path expuesto en el cliente.
- Metadata visible: categoría, última actualización, quién.

### 3. Crear y editar (solo admin)

Formulario con: título, categoría (texto libre con sugerencias de las existentes), y **la elección entre texto o archivo**, excluyente y clara.

- **Editor Markdown** con negritas, listas y títulos. Elegí una librería liviana y **justificá la elección en el reporte**: peso, mantenimiento y que no arrastre HTML crudo. Si no encontrás una que cierre, proponé texto plano con ayuda de sintaxis y avisá — no metas una dependencia pesada por inercia.
- **Archivo:** PDF, Word (`.doc`, `.docx`) y `.txt`. Validación de tipo y tamaño **del lado del server**, con el mismo límite que usa `documents`. Reusá el patrón de subida existente parametrizando bucket y whitelist; **no lo dupliques**.
- **Editar es reemplazo en el lugar**, sin historial de versiones (decisión cerrada del PRD).
- **Al reemplazar un archivo**, borrá el anterior del bucket con la **API de Storage** (no SQL directo: existe el trigger `storage.protect_delete()`). Best-effort: si el borrado falla, la operación **no** se revierte, pero el error tiene que quedar visible en el log. Un archivo huérfano es un problema menor; un procedimiento que no se guarda es uno grande.
- Cambiar de texto a archivo, o al revés, tiene que funcionar y dejar limpio lo anterior.

### 4. Archivar y restaurar (solo admin)

Botón con confirmación. Ida y vuelta entre `vigente` y `archivado`. Copy que deje claro que no se borra nada.

### 5. Aviso in-app

- Badge **"Nuevo"** en la fila mientras hayan pasado menos de 7 días desde `updated_at`.
- Contador o punto en el ítem del menú cuando hay al menos uno nuevo.
- **Usá el helper de fecha del repo con huso `America/Argentina/Buenos_Aires`**, no UTC crudo. Los tests de fecha también.

## Reglas técnicas (no negociables)

- **`createServerClient()`** para todo. **Nunca** `createAdminClient()`: no hay job de sistema acá.
- **Las escrituras van por las RPCs** `crear_procedimiento`, `actualizar_procedimiento`, `archivar_procedimiento`. **No escribas `procedures` con un `.insert()` / `.update()` directo:** la auditoría vive dentro de la RPC y saltearla deja el `audit_log` incompleto.
- **Invocá las RPCs con `createServerClient()`**, no con el admin client: el `service_role` no tiene `sub` en el JWT y la guarda `auth.uid()` abortaría.
- **Contrato return-based (§2.5)** en todas las Server Actions: `{ ok: true, ... } | { ok: false, error }`. Nada de `throw` de mensajes que crucen el límite — en producción Next.js los redacta. Los call sites chequean `!ok`.
- **Errores visibles, nunca tragados.** Distinguí "no hay procedimientos" de "no se pudieron cargar".
- **Filtro de app superpuesto a la RLS** donde corresponda. La RLS ya oculta los archivados a no-admin; el filtro de app va igual, no en lugar de.
- Copy en es-AR en `/lib/copy`, siguiendo la convención. Terminología amigable.
- Sistema de diseño existente. No inventes componentes que ya están.

## Tests

1. **Server Actions:** casos felices y de error de cada una, con el contrato return-based verificado (que devuelvan `{ ok: false }` y no tiren).
2. **RLS por rol, bajo el JWT del rol (`asUser`)**, nunca `service_role`: Empleado y Supervisor no ven archivados y no pueden escribir; el admin sí.
3. **Exclusividad de contenido:** la acción rechaza que vengan texto y archivo a la vez, y rechaza que no venga ninguno.
4. **Validación de archivo:** tipo no permitido y tamaño excedido, los dos rechazados **del lado del server**.
5. **Badge "Nuevo":** dentro y fuera de la ventana de 7 días, con el huso correcto. Incluí el borde exacto.
6. **Sanitización del Markdown:** contenido con HTML o script embebido **no** llega al DOM sin sanitizar. Este test es obligatorio.
7. **Signed URL:** se genera en el server y el path del archivo no queda expuesto en el cliente.
8. **e2e Playwright:** al menos un recorrido por rol — el admin crea, edita y archiva; el empleado ve y busca pero no ve acciones ni archivados. **No rompas el job de e2e.**
