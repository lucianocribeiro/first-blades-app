## 1. Objetivo

La implementación ya mostraba el error en `!ok` en los tres call sites (confirmado por Codex en `FB-F4-AUD-12`). Faltaba **cobertura de tests**: los unitarios existentes verificaban sobre todo que las actions devuelven `{ok:false}` (mockeando Supabase), no que **cada tipo de call site** renderiza ese error de verdad. Sin ese test, un futuro cambio podría volver a tragarse un error sin que nada lo note (aprendizaje Fase 3: errores visibles, no tragados).

Se agregaron tests RTL dirigidos que, con la action mockeada devolviendo `{ ok:false, error:'<texto>' }`, verifican que el componente **muestra** ese error.

## 3. Tests agregados

### `AprobacionesTable` (`call-site-error-visibility.test.tsx`)
`approveAusencia devuelve {ok:false, error} → el error se renderiza, el éxito NO se muestra`: mockea `approveAusencia` (una sola vez) a `{ok:false, error: copy.aprobaciones.messages.alreadyResolved}`, renderiza la tabla con un ítem de ausencia pendiente, hace click en "Aprobar" (interacción real, no simulada a nivel de estado), y verifica que el texto del error aparece en pantalla y que `copy.aprobaciones.messages.resolvedEmailFailed` (la rama de éxito con mail fallido) **no** aparece.

### `SolicitudPasajeForm` (`call-site-error-visibility.test.tsx`)
`la action devuelve {ok:false, error} → el error se renderiza y el éxito NO se muestra`: mockea `createPasajeRequest` a `{ok:false, error: copy.solicitudPasaje.errors.empleadoFueraDeEquipo}`, completa el formulario real (motivo, origen, destino, un día de viaje) para pasar la validación de cliente, envía, y verifica que el error aparece y `copy.solicitudPasaje.messages.success` no.

### `SolicitudAusenciaForm` (`solicitud-ausencia-form.test.tsx`)
`la action devuelve {ok:false, error} → el error se renderiza y el éxito NO se muestra`: el mock del módulo ya resolvía `{ok:true}` por defecto (fix de FB-F4-16) — este test lo sobreescribe UNA vez (`mockResolvedValueOnce`) a `{ok:false, error: copy.solicitudAusencia.errors.pendienteDuplicada}`, completa y envía el formulario real, y verifica que el error aparece y el mensaje de éxito no.

### Verificación de que prueban el render real (no un mock trivial)

Para los tres casos, se **sabotearon temporalmente** los componentes ya arreglados en FB-F4-16 (se les quitó el `if (!result.ok) { ... return; }`/equivalente, dejando que siempre asuman éxito) y se corrió cada test — **los tres fallaron** con el error esperado (`waitFor` con timeout, el texto del error nunca apareció). Se restauraron los tres archivos a su estado correcto inmediatamente después (confirmado sin diff contra HEAD) y se volvió a correr la suite completa en verde. Esto confirma que los tests nuevos **sí** capturarían una futura regresión donde un call site vuelva a tragarse un error — no son mocks triviales que siempre pasan.
